# SMBIOS 机型切换与身份信息

用于用户明确要求换 SMBIOS、生成身份信息，或诊断相关问题时。审查只读；实际改动限于当前任务和已有授权。
换机型前核对已有 ACPI、CPUFriend、内存注入及身份信息的适用性，**不预设这些项目都需要修改**。
参考机器的配置见 [machine-facts.md](machine-facts.md)，不能直接套用。

## 1. 先决策：什么时候该换机型

根据目标 macOS 的支持范围、CPU/GPU 配置、现有电源管理和所需功能比较候选 SMBIOS。
不要仅因显示名、版本号或参考机器采用某机型就切换。

依据：[Dortania SMBIOS 选择指南](https://dortania.github.io/OpenCore-Install-Guide/extras/smbios-support.html)。
系统支持列表和驱动要求会变化，执行时核对目标版本。

### 1.1 升级系统时的两条路线

| 路线 | 适用条件 | 核对内容 |
|---|---|---|
| 保留现有 SMBIOS | 目标系统和所需功能可继续使用 | 是否需要兼容性绕过；相关参数对目标系统、更新器及驱动是否有效 |
| 切换目标 SMBIOS | 有明确兼容性或功能收益，且属于用户请求 | 候选机型支持范围、身份信息一致性、已有注入与回滚路径 |

优先把系统升级和机型切换分开验证，便于定位故障；若用户已明确要求组合迁移，给出分步方案并按授权执行。
不要把 `-no_compat_check` / `revpatch=sbvmm` 当作任何机器的固定方案，细节见
[系统升级指南](os-upgrade-15-to-26.md)。

### 1.2 参考机器的迁移示例

参考机器曾从 `iMacPro1,1` 切到 `MacPro7,1`，之后又切到 `iMac20,1`。
其中处理过 OEM SSDT、CPUFriend 数据和自定义内存信息；这些是那台机器的兼容性处理，
不是每次换 SMBIOS 的必做项目。其电脑名变更也是独立的外观选择。

### 1.3 身份信息与目标 SMBIOS 保持一致

核对 `SystemProductName`、`SystemSerialNumber`、`MLB` 及相关 `PlatformInfo` 字段的对应关系。
需要新身份时，按目标机型生成 serial / MLB，记录旧值供回退；**不要因为换机型就自动轮换 UUID、ROM 或账号状态**。
用户已要求保留的身份字段保持不动；若发现与目标配置存在冲突，先说明具体影响，再决定该项处理方式。

参考机器曾在 `SystemProductName=iMac20,1` 时保留 `MacPro7,1` 序列号，导致「关于本机」显示旧营销名。
这是该次实测，不能推导为所有 macOS 显示名都只由序列号决定，也不能据此要求重生成全部身份字段。

排查显示名时，先核对实际启动的配置、注入值与 serial 产品码，再查缓存：

```bash
macserial -i '<serial>'
```

不要仅为显示名不匹配就清除身份信息、注销 Apple ID 或删除系统偏好。

## 2. 换机型后启动失败：按证据检查 ACPI

### 2.1 先确认故障形态

区分未进入选择器、内核 panic、循环重启和长时间停顿。循环重启是现象，不能仅凭现象认定为看门狗或 ACPI 故障。
取证入口见 [启动失败排查](boot-failure-debug.md)。

### 2.2 OEM SSDT 是检查项

参考 ASUS Z690 的 OEM 表 `xh_adls3` 与 `HS06 AE_NOT_FOUND` 曾在一次迁移中相关，
替换该表后恢复启动。**存在厂商 OEM SSDT 本身不代表有故障**；该案例也不证明 board-id 变化必然使 OEM 表失效。
保留目标机器的原表、错误日志和前后配置差异，确认具体对象与表的关系。

### 2.3 仅在证据指向原表时修补

如果已确认某张 OEM SSDT 的具体错误需要替换，再准备成对配置：

| 位置 | 内容 |
|---|---|
| `ACPI > Delete` | 精确匹配目标表的签名、OEM ID 等条件，避免误删其他表 |
| `ACPI > Add` | 加载为目标机器修正并验证的替换表 |

参考案例的替换表叫 `SSDT-XHADLS3.aml`。不要把这个文件名、ACPI 路径或修改内容照抄到其他主板；
编译、依赖与验证见 [ACPI/SSDT 指南](acpi-ssdt.md)。

### 2.4 怎么确认「是不是它」

| 证据 | 用途 |
|---|---|
| `SysReport` / ACPI 表与 namespace | 确认目标表、对象引用和实际路径 |
| panic / ACPI 错误日志 | 定位失败对象；单条 `AE_NOT_FOUND` 仍不足以证明根因 |
| 可回滚的 A/B 测试 | 比较仅改目标表或 SMBIOS 后的启动结果 |

参考机器的「切换失败 → 修补表 → 启动成功」只作为该案例的证据。

### 2.5 排除因素要针对目标机器

USB 映射、系统根补丁、机型支持范围、NVRAM 和驱动依赖均可按日志检查。
在参考机器上排除过某项，不代表其他机器也已排除；不要把一次 panic 的伴随信息直接当成根因。

### 2.6 USB 映射按已有方案核对

检查当前端口图是否含机型或控制器匹配条件，确认切换后仍匹配目标设备。
没有异常时保留已验证的端口图；需要修改时，使用目标机器的数据，见
[USB 映射指南](usb-port-mapping.md) 和 [USBToolBox README](https://github.com/USBToolBox/kext)。

### 2.7 条件化的迁移顺序

1. 保存可启动基线与完整 EFI 备份，核对待改字段和用户要求保留的字段。
2. 如已有 ACPI 错误，先单独修复并验证；没有证据时不添加 ACPI 改动。
3. 在可回滚候选配置中切换 SMBIOS 与确需匹配的身份字段。
4. 仅对已存在且受机型影响的 CPUFriend、内存或 USB 注入做兼容性调整。
5. 用匹配目标 OpenCore 版本的校验器检查，再测试启动和请求涉及的功能。

### 2.8 换机型前的检查清单

- [ ] 记录当前与目标 SMBIOS，确认本次实际改动范围。
- [ ] 完整 EFI 备份与可用的恢复入口已准备好。
- [ ] 仅当日志指向 ACPI 时，定位具体表和对象。
- [ ] 已有 CPUFriend / 内存 / USB 注入的匹配条件已核对。
- [ ] 计划中的 serial / MLB 与目标机型对应；UUID、ROM 等保留项已记录。

## 3. 机型相关配置：检查已有项，再决定是否修改

### 3.1 相关项清单

| 项目 | 处理条件 |
|---|---|
| serial / MLB | 核对与目标 SMBIOS 的对应关系；仅按本次授权替换 |
| OEM SSDT / 其他 ACPI 补丁 | 有具体错误或机型匹配条件时处理 |
| `CPUFriendDataProvider` | 已使用自定义数据时核对来源、目标机型和实测效果，必要时重建或回退 |
| 自定义内存注入 | 已启用 `CustomMemory` 时核对目标显示与配置，不为换机型新加注入 |
| UUID / ROM | 保持稳定；仅在任务需要且已获授权时调整 |
| 电脑名 / 主机名 / SMB 名 | 独立偏好，只在用户要求改名时处理 |
| 显示名缓存 / `ByHost` 偏好 | 有具体异常时再诊断，不默认删除或重置 |

CPUFriend 作者明确提醒多数机器无需自定义电源数据。没有使用 CPUFriend 时，不因机型切换而默认安装；
已使用时也不把参考机器的 `hwp` 删除方案直接套用。
依据：[CPUFriend Instructions](https://github.com/acidanthera/CPUFriend/blob/master/Instructions.md)。
内存字段见 [内存注入指南](memory-injection.md)，睿频案例见 [Intel 电源管理](intel-turbo.md)。

### 3.2 电脑名属于独立设置

`ComputerName`、`LocalHostName`、`HostName` 与 SMB 文件共享名不随 SMBIOS 自动改名。
用户要求改名时先读取现值，只修改请求涉及的名称；沿用用户选择，不照抄作者的设备名。
不要因迁移 SMBIOS 删除旧偏好文件、强制设置 `HostName` 或重新登录 iCloud。

## 4. 切换工具与救援路径

本技能未附带专门的 SMBIOS 切换脚本。需要实现辅助工具时，可采用以下接口，不能假定示例工具已存在：

| 模式 | 行为 |
|---|---|
| `plan`（默认） | 只读检查，列出字段差异、候选哈希与保留项；公开输出脱敏 |
| `apply` | 确认 live 基线未变化，备份后写入已验证的候选配置 |
| `rollback` | 确认目标与备份后恢复；遇到用户或其他进程已还原的状态，不覆盖重写 |

使用 [安全编辑包装](../scripts/oc-edit-safe.sh) 前先查看参数，按 `begin` / `finish` 执行；修改前先准备并审阅候选差异。
按分区 UUID、设备信息和实际 EFI 内容确认目标，不能只凭固定盘号或第一个 EFI 分区。
恢复副本应在系统无法启动时仍可读取；写入后按 [安全工作流](../SKILL.md) 校验并复验落盘。

## 5. 身份信息：生成、核对与 ROM

### 5.1 生成

需要新身份时使用 OpenCore 自带 `macserial` 或 [GenSMBIOS](https://github.com/corpnewt/GenSMBIOS)，
按目标机型生成 serial / MLB，并用 `macserial -i '<serial>'` 核对对应关系。
UUID、ROM 分别核对与决定，不因工具能生成就覆盖稳定的现值。

### 5.2 序列号查询的边界

[Dortania iServices 指南](https://dortania.github.io/OpenCore-Post-Install/universal/iservices.html#serial-number-validity)
说明了 Apple 保修查询结果的差异。查询不到保修信息不能证明序列号永远未被使用，
「购买日期未验证」也不是无冲突保证；不要复用真实设备的身份或把查询结果当作账号服务可用性承诺。

### 5.3 ROM：核对稳定值，不随 `en0` 自动轮换

先读取当前 ROM，检查其数据类型与长度；需要设置新值时，Dortania 的修复流程采用网卡 MAC 转换。
但同一指南也提到其他选值方式，不能把「必须等于当前 `en0` 真实 MAC」写成 OpenCore 的普适要求。
`en0` 可以是有线、无线或雷雳网卡，无需为换机型强制把 Wi-Fi 排到 `en0`。
依据：[Dortania iServices](https://dortania.github.io/OpenCore-Post-Install/universal/iservices.html#fixing-rom)。

网卡顺序变化时先记录与诊断，不自动改 ROM。授权修改后，使用 plist 工具保留 `Data` 类型，
检查解码后的 6 字节数据和语义 diff，避免仅凭 base64 字符串长度判断正确性。

### 5.4 身份变更后的验证

记录旧值与新值，重启核对实际注入和请求涉及的功能。身份变更可能影响账号认证或按 UUID 保存的偏好；
不要预设必然重建所有偏好，也不要自动清理钥匙串、消息记录或重登账号。

### 6.1 网卡接口顺序变化后的处理

对照原记录检查 `en0`、built-in 标记与服务症状。网络接口重排和 ROM 变更是独立操作，
不要因为驱动顺序变化就默认删除网络偏好或重建机器身份。
相关背景见 [网络接口顺序](network-en0-order.md)，实际要求以对应版本上游文档和目标机器证据为准。
AirDrop / 接力故障先走 [连续互通排查](airdrop-handoff.md)，不要以此为由先改身份信息。

## 7. 操作中的证据边界

- live EFI 与预期不符时重新读文件、挂载信息与差异；可能是用户已回退，不要自动覆盖。
- 不能仅用配置字节数判断启动时使用的是哪份文件；相同大小的内容仍可能不同。
- 保留改前哈希、配置差异、引导日志和启动后的实际机型信息，组合判断本次迁移是否生效。
